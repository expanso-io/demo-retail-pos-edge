Card data stays in the store

Card data never leaves the store as a card number: each swipe becomes a one-way join ID with its context, checked before it touches the core network.

A retail and payments group wants its card transactions to improve search, recommendations and personalisation, but card data may not leave the card business. Each store has an Expanso Edge node that runs two jobs. Everything between a till and the warehouse is pipeline configuration.

  1. Anonymised at the source. The card number becomes a join ID, every card and person field is stripped, SKUs become product names, and the store, till, location, local time and temperature are added.
  2. Untrusted tills are checked before the DMZ. Signature, schema, totals, age and text fields are verified; a final scan blocks any card number in any field. What fails stays in the store with its reason.
  3. Collection survives stopped jobs. Tills commit to a store database while Expanso is stopped; starting the jobs collects the backlog.
  4. Outages queue locally, delivery is encrypted and authenticated. Clean records wait on the store's disk and cross the WAN once, over TLS 1.3 with a client certificate per store. The warehouse stores each transaction ID once.

Deploy it

3. Deploy the jobs from Expanso Cloud

Put the three Expanso values in .env (owner-only; it is never committed). just up deploys both jobs stopped, connects a node per store, and starts the registers and the warehouse. Start pos-guard and pos-uplink in the Cloud console, or run just start-jobs.

cp env.example .env && chmod 600 .env
just up
just start-jobs

4. Deploy to a store

Both jobs select nodes labelled role: pos-store. Each job reads its node's environment; the job files only name these variables.

Environment the jobs read on each store node
VariableJobWhat it is
STORE_IDbothThe store, for example s1. Used in the source path and every record's context.
STORE_SOURCE_URLguardThe store database API: leases events, serves telemetry, takes acknowledgements. Defaults to http://127.0.0.1:8642.
POS_CONFIG_DIRguardDirectory with this store's configuration, read at run time: register-keys.json (register ID to enrolled signing key; a register not listed is quarantined as not enrolled), join-id-key.txt (the group's join key, the same at every store), store-profile.json (store ID, name, district, country, time zone, latitude, longitude) and store-catalog.json (SKU to product name and category). Create it owner-only, mode 0700 with 0600 files. If it is missing, every swipe is quarantined: the job never runs on keys it was not given. The default points into this repository's fixtures, which a store node does not have.
QUARANTINE_FILEguardPath on the store's disk where quarantined records are appended.
DISPLAY_URLguardThe store's window display endpoint; receives the sales window and the register roster.
OUTBOX_URLguardWhere pos-guard hands clean records to pos-uplink on the same node.
OUTBOX_ADDRuplinkThe address pos-uplink listens on for that hand-off. Loopback only.
UPLINK_QUEUE_DBuplinkPath of the durable queue on the store's disk. Records leave it only after the warehouse answers.
WAREHOUSE_HOSTuplinkHost and port of the warehouse's TLS ingest, for example the store's WAN link. The job adds https:// and /ingest.
WAREHOUSE_CA_FILEuplinkThe group's certificate authority. The node trusts only this for the warehouse.
STORE_CLIENT_CERT_FILEuplinkThis store's client certificate; its common name is the store ID.
STORE_CLIENT_KEY_FILEuplinkThe matching private key. Mode 0600, readable only by the account that runs the node.

Deploy the two job files with explicit credentials, never a stored profile:

for job in pos-guard pos-uplink; do
  expanso-cli --endpoint "$EXPANSO_CLI_ENDPOINT" \
    --api-key "$EXPANSO_CLI_API_KEY" \
    job deploy "pipelines/$job.yaml"
done

5. Run the warehouse side

The ingest port speaks only TLS 1.3 and requires a client certificate issued by the group's authority. A certificate is for one store: a batch carrying another store's records is refused. The read API is a separate loopback listener and cannot ingest. Issue the certificates once; copy each store its own clients/<store>.pem and .key and the authority's ca.pem. The authority's key stays on the warehouse side.

uv run -s scripts/pki.py init .secrets/pki s1 s2 s3 s4
uv run -s scripts/warehouse.py --port 8641 \
  --tls-cert .secrets/pki/warehouse.pem \
  --tls-key .secrets/pki/warehouse.key \
  --client-ca .secrets/pki/ca.pem

The warehouse binds to loopback unless you pass --bind with the interface address in the DMZ. Its database is a SQLite file under .runtime by default; pass --db to put it on durable storage.
